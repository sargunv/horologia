> Generated by /craft · Started: 2026-04-21

## Task

Implement the mobile login flow per `mobile/design/login-flow.html`.

**Scope — what to build:**

- Server picker screen (new): Compact and Expanded layouts (WindowSizeClass / horizontalSizeClass).
  Single URL field with debounced probe (600ms), 6 states per § C (empty / typing / probing / valid
  / invalid-unreachable / invalid-wrong-server). Default scheme to `https://` on bare host. No
  network-range validation — accept any URL, any scheme.
- OAuth browser handoff per § D: ASWebAuthenticationSession on iOS, Custom Tabs on Android, loopback
  redirect on desktop. PKCE + state. Callback `horologia://oauth` on mobile,
  `http://127.0.0.1:<port>` on desktop.
- Finishing sub-state per § E: token exchange → secure-store write → parallel cache warm-up
  (`/api/profile` + `/api/spaces`) → 300ms minimum dwell.
- Cold-launch routing per § H: has-server? has-token? → silent refresh → Profile (cached) or
  ServerPicker.
- Drop the dev-token bootstrap: remove `HOROLOGIA_DEV_TOKEN` from
  `ApiBootstrapKt.configureHorologiaApi` callsites; the `getToken` closure reads from the new
  session store.
- Profile surface unchanged — today's placeholder stays. Redesign is the next task.

**Libraries / platform targets to bump:**

- Compose `androidx.compose.material3` to a version shipping Material 3 Expressive (LoadingIndicator
  with wave, expressive shape/motion theme, MaterialExpressiveTheme if that's the API). Apply to
  `:compose-app` (Android + desktop). Also pull in `material3-adaptive` /
  `material3-window-size-class` if not already present.
- iOS: bump `iosApp` deployment target to iOS 26 in `project.yml` and the KMP `iosMain` linker
  target in `mobile/core/build.gradle.kts` / `mobile/gradle/libs.versions.toml` so SwiftUI Liquid
  Glass (`.glassEffect()`, tinted glass materials, `GlassEffectContainer`) is available. Use them on
  the login surface where they improve it; don't force glass on read-heavy surfaces.

**Platform cleartext config:**

- Android: `network_security_config.xml` with `cleartextTrafficPermitted="true"` globally.
- iOS: `NSAppTransportSecurity` dict with `NSAllowsArbitraryLoads = true` in `iosApp/project.yml`
  Info.plist.
- No app-layer URL-shape validation.

**Likely blocker the pipeline must surface during explore/clarify (P0):** The server today has
cookie-based `POST /app/auth/login` + `POST /api/auth/tokens` (mints bearer from cookie), not OAuth
with PKCE. The spec assumes OAuth. The architect phase has to pick one: (a) add server-side OAuth
endpoints (bigger scope; may need a separate task), (b) drive the existing cookie flow through the
system browser and terminate with a server-side redirect to `horologia://oauth?token=…`, (c) change
the plan (e.g., in-app form, but that violates design principle #2). Expect this to shape the
architecture phase.

Context: mobile project at `mobile/`. `:core` is the shared KMP library (ViewModels + OpenAPI
client + AppContainer). `:compose-app` is Compose for Android + desktop. `iosApp/` is SwiftUI
consuming `HorologiaCore.xcframework`. Today's `ProfileViewModel` / `SpacesViewModel` +
per-destination `ViewModelStoreOwner` pattern (landed in commit `a7a1e94`) is the template for
`LoginViewModel`. Navigation: Compose Navigation on Android/desktop, SwiftUI `NavigationStack` on
iOS.

Commits style reference: recent mobile commits in `git log --oneline`.

Design spec: `mobile/design/login-flow.html` (wireframe spec — structure, copy, states, responsive
rules, platform primitives).

## Exploration Report

### Key Facts (most actionable first)

- **The "likely P0 blocker" framing in the task is wrong.** `server/internal/api/oauth.go:97-125`
  mounts a full OAuth 2.1 authorization server with PKCE S256, metadata discovery at
  `/.well-known/oauth-authorization-server`, and public-client auth
  (`"token_endpoint_auth_methods_supported": ["none"]`). Landed in PR #53 (`0bcb295`). **Mobile can
  speak OAuth directly; no server-side OAuth work needed for the happy path.**
- **Server redirect matcher is loopback-only** (`server/internal/api/oauth.go:693-714`): accepts
  exact matches against `OauthClient.RedirectUris` OR (if `LoopbackRedirects=TRUE`) any `http://`
  URI with a `localhost` or loopback IP host. Custom schemes like `horologia://oauth` are not
  accepted today — either the seeded client's `redirect_uris` array gets the custom scheme added (a
  migration), or the matcher learns to allow custom-scheme exact matches, or mobile uses loopback on
  Android/iOS too (unusual).
- **Only one OAuth client is seeded**
  (`server/internal/database/migrations/00001_initial.sql:319-337`): `horologia-cli`,
  `redirect_uris='{}'`, `loopback_redirects=TRUE`, no client secret, `is_first_party=TRUE`. No
  `horologia-mobile` row — architect must decide whether to reuse `horologia-cli` or seed a distinct
  client.
- **OAuth endpoints are NOT in TypeSpec** (`api/src/auth.tsp`). They're hand-registered.
  Consequence: the generated `AuthApi` Kotlin client cannot call `/oauth/authorize` or
  `/oauth/token` — mobile will need to hit them via Ktor directly (Ktor is already a transitive dep
  via `openapi-kmp-gen:companion` v1.3.0, no explicit pin).
- **No `/api/meta` endpoint exists.** `/healthz` is mounted at root, outside `/api`. The
  design-spec's "server probe" target should be `GET /app/auth/config` (`api/src/auth.tsp:87-89`,
  `@useAuth(NoAuth)`) — it returns
  `AuthConfig { oidc:{enabled,label,autoRedirect}, password:{enabled} }` and is the natural "is this
  a Horologia server" probe. Landing on this also tells the client whether the server supports
  password + OIDC before OAuth starts.
- **Prior-art OAuth+PKCE+loopback client exists at `cli/`** (PR #53). The mobile desktop target can
  mirror its loopback listener; mobile iOS/Android translate the same PKCE + state logic to
  `ASWebAuthenticationSession` / Custom Tabs.
- **Canonical ViewModel template** lives at
  `mobile/core/src/commonMain/kotlin/dev/horologia/mobile/core/feature/profile/ProfileGateway.kt:11-45`
  and `ProfileViewModel.kt:11-43`. Shape: `internal interface FeatureGateway` + `FetchXxxResult`
  sealed 4-case (`Ok`, `AuthFailure`, `Retryable`, `Permanent`) +
  `internal class LiveFeatureGateway` + `class FeatureViewModel(gateway)` with
  `MutableStateFlow<UiState>` + `init { refresh() }` + cancel-safe `refresh()`. New
  `LoginViewModel` + `ServerProbeViewModel` mirror this verbatim.
- **`ApiBootstrap.configureHorologiaApi(baseUrl, getToken)` mutates a process-global singleton**
  (`mobile/core/src/commonMain/kotlin/dev/horologia/mobile/core/ApiBootstrap.kt:14-22`). `baseUrl`
  is `override var` (writable); `getToken` is a closure evaluated per request; `Auth.BearerAuth` can
  be added/cleared atomically. **Server switch and token swap are both cheap**, but today's
  callsites capture compile-time-constants — they need to read from a mutable holder.
- **Three dev-token callsites** all carry the same TODO
  (`mobile/compose-app/.../MainActivity.kt:10-18`, `.../desktopMain/.../Main.kt:10-14`,
  `mobile/iosApp/iosApp/HorologiaApp.swift:7-21`). All three disappear when the session-backed
  provider lands.
- **Compose M3 is JetBrains Compose Multiplatform, not androidx.**
  `mobile/gradle/libs.versions.toml:35` pins `org.jetbrains.compose.material3:material3:1.9.0`. The
  androidx `material3` entry (`:23`) is declared but unreferenced. M3 Expressive availability in CMP
  must be confirmed against
  [JetBrains CMP release notes](https://github.com/JetBrains/compose-multiplatform/releases) — not
  locally verifiable. Androidx `material3` 1.4+ has `MaterialExpressiveTheme` and the wave
  `LoadingIndicator` (annotated `@ExperimentalMaterial3ExpressiveApi`); CMP historically lags by a
  minor version or more.
- **iOS deployment target is 17.0** (`mobile/iosApp/project.yml:5`). Liquid Glass (`.glassEffect()`,
  `GlassEffectContainer`) requires iOS 26 / Xcode 26 / SwiftUI 7. KMP `:core` sets no explicit iOS
  min-version — defaults to Kotlin/Native's baseline (iOS 14 in Kotlin 2.3.x). The Xcode-layer
  deployment target is the binding constraint at load time.
- **No `CFBundleURLTypes` and no Android deeplink intent-filter.** `mobile/iosApp/project.yml:29-36`
  has no `urlSchemes` section. `mobile/compose-app/src/androidMain/AndroidManifest.xml:13-22` has
  only `MAIN`/`LAUNCHER`. Custom-scheme redirects require adding both.
- **`androidx.browser:browser` is not in the catalog.** Custom Tabs support on Android needs a new
  dep.
- **Persistence is greenfield in `:core`.** Zero matches for
  `DataStore | SharedPreferences | NSUserDefaults | Keychain | multiplatform-settings | SecureRandom | MessageDigest | androidx.security.crypto`.
  No expect/actual declarations anywhere; `:core/src/` has only `commonMain`, `commonTest`,
  `iosMain` directories. Session-token storage, PKCE SHA-256, and server-URL persistence are all new
  builds.
- **No existing cache in the gateways.** `LiveProfileGateway.fetchMe()` hits `UsersApi.usersMe()`
  every call; `LiveSpacesGateway.fetchSpaces()` same. The design spec's "warm up existing `:core`
  cache" (`mobile/design/login-flow.html` § G) is aspirational —

- **`CallExceptionClassifier.classify()` already buckets 401/403 to `Failure.Auth`**
  (`mobile/core/.../net/CallExceptionClassifier.kt:14-47`). A silent-refresh interceptor has an
  obvious hook, but today gateways propagate `AuthFailure` unmodified.
- **Compose NavHost `startDestination = ProfileRoute` is hardcoded**
  (`mobile/compose-app/.../HorologiaApp.kt:25`). No signed-in-vs-signed-out branching exists. iOS
  equivalent: `NavigationStack { ProfileView() }` in `HorologiaApp.swift:25`. Cold-launch routing to
  Login vs. Profile will live at these two sites plus their desktop sibling.
- **`network_security_config.xml` already permits cleartext for `10.0.2.2` + `localhost`.** Matches
  iOS `NSAllowsLocalNetworking: true`. For the design-spec's "accept any URL" rule, both need
  broadening to arbitrary hosts (`cleartextTrafficPermitted="true"` globally on Android,
  `NSAllowsArbitraryLoads=true` on iOS).
- **iOS screen template**: `mobile/iosApp/iosApp/ProfileView.swift:5-19` shows the per-view
  `@StateObject IosViewModelStoreOwner` +
  `.task { for await newState in viewModel.uiState { ... } }` pattern. New `LoginView` mirrors it.
- **No mobile-side logging facility** — zero uses of `Log.` / `Logger` / `println` in `:core`.
  Auth-flow telemetry (if any) starts from scratch.

```go
func oauthRedirectURIAllowed(client dbgen.OauthClient, redirectURI string) bool {
    if slices.Contains(client.RedirectUris, redirectURI) {
        return true
    }
    if !client.LoopbackRedirects {
        return false
    }
    u, err := url.Parse(redirectURI)
    if err != nil || u.Scheme != "http" {
        return false
    }
    host := u.Hostname()
    if host == "localhost" { return true }
    ip := net.ParseIP(host)
    return ip != nil && ip.IsLoopback()
}
```

```kotlin
internal interface ProfileGateway {
  suspend fun fetchMe(): FetchProfileResult
}

internal sealed interface FetchProfileResult {
  data class Ok(val displayName: String) : FetchProfileResult
  data object AuthFailure : FetchProfileResult
  data class Retryable(val message: String) : FetchProfileResult
  data class Permanent(val message: String) : FetchProfileResult
}

internal class LiveProfileGateway(private val requestTimeout: Duration = 15.seconds) :
  ProfileGateway {
  override suspend fun fetchMe(): FetchProfileResult = try {
    withTimeout(requestTimeout) {
      UsersApi.usersMe().fold(
        ifRight = { FetchProfileResult.Ok(displayName = it.data.name) },
        ifLeft = { exception -> when (val failure = exception.classify()) {
          Failure.Auth -> FetchProfileResult.AuthFailure
          is Failure.Retryable -> FetchProfileResult.Retryable(message = failure.message)
          is Failure.Permanent -> FetchProfileResult.Permanent(message = failure.message)
        }},
      )
    }
  } catch (_: TimeoutCancellationException) {
    FetchProfileResult.Retryable(message = "Request timed out after $requestTimeout.")
  }
}
```

### Server picker screen

**R1:** A new `ServerPicker` screen is the app's entry point when no session exists. It contains a
single URL text field, a primary "Continue" button, and a supporting-text row under the field that
reports probe state. Source: human confirmed (design spec § C) Verification: grep for `ServerPicker`
in `:compose-app` and `iosApp`; visual inspection against `mobile/design/login-flow.html` § C.

**R2:** `ServerPicker` renders a **Compact** layout (single-column, full-viewport) below a 600 dp /
`.compact` breakpoint and an **Expanded** layout (centered card, max-width ~480 dp, two-pane on
larger viewports) at or above. Branches on Compose `WindowSizeClass.widthSizeClass` and SwiftUI
`@Environment(\.horizontalSizeClass)`. One view hierarchy per platform, branched internally. Source:
human confirmed (design spec § C.01.a / 01.b) Verification: resize window / rotate tablet / unfold
foldable in preview or runtime — layout visibly switches at the breakpoint.

**R3:** When the user omits the scheme (e.g., types `tasks.example.com`), probe uses `https://`.
Typed `http://` and `https://` are honored exactly. No network-range validation, no rejection based
on URL shape. Source: human confirmed (earlier conversation) Verification: unit test on the URL
parser in `:core`; manual probe of `localhost:8080`, `http://192.168.x.x`, `https://example.com`.

**R4:** Probe target is `GET /app/auth/config` on the user-supplied base URL. A 200 response that
deserializes as `AuthConfig { oidc, password }` confirms a Horologia server; any other response
(timeout, non-200, malformed JSON, wrong shape) routes to `Invalid · wrong server` or
`Invalid · unreachable`. Source: craft-clarify recommendation (only viable unauth endpoint per
exploration) Verification: unit test on the server-probe gateway using a fake HTTP response;
integration test against dev server.

**R5:** The field transitions through exactly 6 states per design spec § C: `Empty`, `Typing`,
`Probing`, `Valid`, `Invalid · unreachable`, `Invalid · wrong server`. Probe debounces at 600 ms
after the last keystroke (or fires immediately on blur). Continue is enabled only in `Valid`.
Source: human confirmed (design spec § C states) Verification: `ServerProbeViewModelTest` asserts
state transitions for each path (kept/dropped keystrokes, success, failure, malformed response).

### OAuth flow

**R6:** The flow uses OAuth 2.1 Authorization Code with **PKCE S256** and the **`state`** parameter.
`code_verifier` (43–128 chars, base64url) is generated at browser-launch time, held in memory only,
and cleared on completion (success, failure, or timeout). `state` is a fresh random value; callbacks
with a mismatched `state` are treated as hostile — PKCE state dropped, user returned to ServerPicker
with a banner. Source: craft-clarify recommendation (security baseline; matches server's advertised
`code_challenge_methods_supported: ["S256"]`) Verification: unit test on PKCE verifier generation
and `code_challenge` derivation; test that callback with wrong state transitions to error.

**R7:** Redirect URI is **`horologia://oauth`** on iOS and Android and
**`http://127.0.0.1:<random-port>/`** on desktop. Mobile uses custom scheme; desktop uses loopback.
Source: human confirmed (Q1) Verification: grep for the callback strings in iOS/Android/desktop
entry points; inspect OAuth authorize URL built by the client.

**R8:** A new OAuth client `horologia-mobile` is seeded via a fresh Goose migration in
`server/internal/database/migrations/`:

- `client_id = 'horologia-mobile'`
- `display_name = 'Horologia'`
- `redirect_uris = '{horologia://oauth}'`
- `loopback_redirects = TRUE` (covers desktop)
- `client_secret_hash = NULL`
- `is_first_party = TRUE` Source: human confirmed (Q1) Verification: new migration file exists;
  `SELECT * FROM oauth_clients WHERE client_id='horologia-mobile'` against a fresh-migrated dev DB
  returns the expected row.

**R9:** Browser primitive per platform:

- **iOS:** `ASWebAuthenticationSession` with `prefersEphemeralWebBrowserSession` default true;
  callback caught by the session's completion handler (not Universal Links / scene delegate).
- **Android:** `androidx.browser.customtabs.CustomTabsIntent` for the outbound tab; callback arrives
  via an intent-filter on a handler activity that routes back into the same `LoginViewModel`.
- **Desktop:** `java.awt.Desktop.browse()` (or equivalent) for the outbound browser; callback caught
  by a short-lived `com.sun.net.httpserver.HttpServer` bound to `127.0.0.1:<random-port>` that
  returns a minimal "You may close this tab" response and shuts down within 5 s of a valid callback.
  Source: human confirmed (design spec § D + Q1) Verification: grep for each primitive; manual
  trace-through on each platform.

**R10:** Finishing sub-state: on callback OK, the client exchanges code at `POST /oauth/token` with
the stored `code_verifier`, parses access + refresh tokens and TTL, persists them to the OS secure
store keyed by server host, then routes to Profile. A minimum dwell of 300 ms is enforced so the
transition reads as deliberate. Source: human confirmed (design spec § E) Verification: unit test on
the finishing state machine; measure dwell in manual trace (should never be under 300 ms).

**R11:** No profile / spaces cache warm-up during the finishing sub-state. Profile renders its usual
first-load on arrival. Source: human confirmed (Q2 — explicitly deferred) Verification: grep for
`/api/profile` calls during finishing — should be zero; Profile's existing `fetchMe()` runs on mount
as today.

### Persistence & cold launch

**R12:** Tokens (access + refresh) persist in the OS secure store, keyed per server host:

- **iOS:** Keychain via `Security.framework` `actual`, `kSecAttrAccessibleAfterFirstUnlock`.
- **Android:** `EncryptedSharedPreferences` via `androidx.security.crypto` (or a Tink-backed
  alternative picked during architect phase).
- **Desktop:** macOS Keychain, Windows Credential Manager, libsecret on Linux — whichever
  cross-platform KMP / JVM library is chosen during architect phase. Fallback to an encrypted file
  with a user-derived key is acceptable where a vault is unavailable. Source: human confirmed
  (design spec § G) Verification: manual inspection of secure-store entry on each platform; tokens
  persist across app restart.

**R13:** The current server URL (plain string) persists in platform app-prefs: DataStore on Android,
UserDefaults on iOS, a file-based JVM preferences mechanism on desktop. PKCE verifier and state live
in process memory only. Source: human confirmed (design spec § G) Verification: inspect written
prefs; confirm PKCE values never appear on disk.

**R14:** Cold-launch routing runs before first frame paint:

- No saved server → ServerPicker (empty).
- Server saved but no refresh token → ServerPicker with URL pre-filled.
- Both present → fire silent refresh: success → Profile; failure → ServerPicker with banner "Signed
  out." Source: human confirmed (design spec § H) Verification: integration trace for each branch on
  fresh-install and on a corrupted-session simulation.

## Architectural Decision

- **Chosen approach:** Composite — Pragmatic core with Robust edges
- **Core idea:** One `LoginViewModel` owns the whole flow (server-picker state machine + PKCE +
  browser + token exchange + finishing dwell) following the existing `feature/profile` template
  byte-for-byte; four `expect/actual` platform contracts (`SessionStore`, `ServerPrefs`,
  `BrowserLauncher`, `Crypto`) cover persistence, browser, and hash/random;
  `ApiBootstrap(baseUrl, getToken)` signature unchanged (per-request `DefaultRequest` block verified
  in Ktor 3.4.2 bytecode, so re-calling to swap baseUrl works); dedicated Android
  `OAuthRedirectActivity` keeps the back-stack clean; AES-GCM file on desktop satisfies R12's
  fallback clause.
- **Approved:** 2026-04-21

### Approaches Considered

- **Minimal** — single VM, 5 `expect/actual` contracts, plain-0600 desktop store, JDK HttpServer.
  Lost on desktop security (plain file vs encrypted) and Android back-stack robustness.
- **Cleanest/Robust** — two VMs, 6 contracts + reactive `SessionHolder`-driven bootstrap, Ktor CIO
  desktop server, silent-refresh interceptor. Lost on VM split (violates codebase 1-VM-per-screen
  convention) and `ApiBootstrap` signature churn (no correctness gain; verified per-request block
  read in Ktor).
- **Pragmatic** — single VM, one `SessionStore` contract, MainActivity `onNewIntent` routing, JDK
  HttpServer. Lost on embedding browser logic at screen layer (should be a platform contract) and
  Android back-stack bug from routing OAuth through MainActivity.

### Key trade-offs resolved

- **Single VM vs. split:** Single wins on codebase convention (1 VM per screen in `feature/profile`,
  `feature/spaces`).
- **`ApiBootstrap` signature:** Unchanged, because Ktor 3.4.2's `DefaultRequest.Plugin.install.1`
  bytecode confirms per-request block invocation — `Api.baseUrl` mutation takes effect on next
  request.
- **Desktop secure store:** AES-GCM with per-install random key file (R12 fallback clause) — cheap
  encryption over plain JSON.
- **Desktop loopback:** JDK `com.sun.net.httpserver.HttpServer`, not Ktor CIO. Zero new deps;
  consistency argument doesn't justify 2+ new libs.
- **Android OAuth redirect:** Dedicated `OAuthRedirectActivity` with `taskAffinity=""`, not
  `MainActivity.onNewIntent`. Prevents back-stack bug when user backgrounds app mid-flow.
- **Silent-refresh mid-session:** Deferred. Cold-launch refresh only this task; mid-session 401
  surfaces `AuthFailure` and user re-signs-in.
- **Cold-launch timing:** Optimistic Profile render + background refresh, not blocking on refresh.
  Decision step itself is `runBlocking` (prefs+store read, sub-50 ms, no network).
- **DB migration:** Squashed into `00001_initial.sql` per backend's pre-prod convention. Re-login
  friction is identical either way because DB reset wipes `auth_tokens` regardless.
- **TanStack-Query-style data layer:** Explicitly deferred to a follow-up `/craft`. Login has no
  cache semantics worth that scope expansion.

### Adversarial finding

- **Severity:** P2 (verified safe). Original claim that `Api.baseUrl` reassignment would be a dead
  store was based on older Ktor behavior. Disassembly of `io.ktor:ktor-client-core-jvm:3.4.2`'s
  `DefaultRequest$Plugin$install$1.class` (offsets 54–118) shows a fresh `DefaultRequestBuilder`
  constructed per request, with `plugin.block(freshBuilder)` invoked dynamically — meaning
  `apiConfig$lambda$1`'s `url.takeFrom(getBaseUrl())` reads `Api.baseUrl` on every outbound call.
  Multi-call `configureHorologiaApi` is safe.
- **Addressed by:** `ApiBootstrapTest` (commonTest) rebases the client through two different URLs
  and asserts `MockEngine` sees the second host. Guards against a future Ktor upgrade reverting to
  install-time URL capture. `ApiBootstrap.kt` doc comment updated to record the behavior assumption.
