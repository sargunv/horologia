## Requirements

R1: Staleness is computed on the frontend as `(now - anchor) / interval`, where anchor is
`lastCompletedAt` (or `createdAt` if never completed) and interval is derived from the recurrence
rule. Source: human confirmed (BRIEF formula + Q2 fallback approved) Verification: A staleness
utility function exists that returns a percentage, using `createdAt` when `lastCompletedAt` is null.

R2: Staleness only applies to recurring tasks (`recurrenceType !== "one_off"`). One-off tasks and
tasks without a recurrence rule show no staleness indicator. Source: craft-clarify recommendation
(BRIEF: "Applies to all recurring task types") Verification: TaskRow renders no staleness border for
one-off tasks.

R3: Staleness is rendered as a thin left border (3–4px) on each TaskRow, with the border color
interpolated from green → yellow → red based on staleness percentage. A tooltip on hover shows the
staleness percentage. Source: human confirmed (Q1 approved) Verification: TaskRow has a left border
whose color varies with staleness; hovering shows a percentage tooltip.

R4: The recurrence interval is derived using the `rrule` library by computing the next occurrence
after the task's anchor date, giving the cycle-specific interval `(nextDue - anchor)` rather than a
generic fixed interval. Source: human adjusted (original two-occurrence approach fails for multi-day
rules like BYDAY=MO,TU) Verification: Interval computation handles irregular-spacing rules correctly
by using anchor-relative next occurrence.

R5: The `show_staleness` per-task toggle is deferred. Staleness is shown unconditionally for all
recurring tasks in this PR. Source: human confirmed (Q3 approved) Verification: No `show_staleness`
field added to DB, TypeSpec, or API. No toggle UI exists.

R6: Tasks with staleness in a completion-category status do not show the staleness indicator (they
are "done" — staleness resets on next status change back to initial/intermediate). Source:
craft-clarify recommendation (BRIEF: completion triggers "staleness reset") Verification: TaskRow
hides the staleness border when the task's status category is "completion".

## Architectural Decision

**Chosen approach:** Clean/Robust (simplified API) **Core idea:** Dedicated `staleness.ts` module
with pure functions for staleness computation and color mapping, consumed by TaskRow via an
absolutely-positioned indicator div with IconTooltip. **Approved:** 2026-04-12

### Approaches Considered

**Minimal:** Add functions to existing `dates.ts`, apply `borderLeft` inline style on Link, native
`title` tooltip. Smallest diff but introduces `rrule` dependency into `dates.ts` and creates visual
inconsistency (native tooltip vs styled IconTooltip elsewhere).

**Clean/Robust (chosen):** Separate `staleness.ts` module, absolutely-positioned indicator div,
IconTooltip for styled tooltip, injectable `now` for testing. Follows codebase convention of
one-concept-per-lib-file.

### Requirement Coverage

- R1: `computeStaleness` in `staleness.ts` — returns `(now - anchor) / (nextDue - anchor)`
- R2: Guard clause returns null for `recurrenceType === "one_off"` or `recurrenceRule === null`
- R3: Absolutely-positioned 3px div with inline `backgroundColor`, wrapped in `IconTooltip`
- R4: `computeNextOccurrence` finds the next rrule occurrence after the anchor date, giving
  cycle-specific interval
- R5: No toggle code — staleness shown unconditionally for qualifying tasks
- R6: Guard clause returns null when `statusCategory === "completion"`

### Key trade-offs resolved

- **File organization:** Separate `staleness.ts` over adding to `dates.ts` — keeps `rrule`
  dependency isolated, matches codebase pattern of one-concept-per-file.
- **Border rendering:** Absolutely-positioned inner div over `borderLeft` on Link — avoids layout
  shift and border conflicts with card container.
- **Tooltip:** `IconTooltip` over native `title` — matches all other tooltips in TaskRow for visual
  consistency.
- **Interval computation:** Anchor-relative next-occurrence over fixed-epoch two-occurrence diffing
  — correctly handles irregular-spacing rules (e.g., BYDAY=MO,TU) by computing the specific cycle
  interval for each task instance.

### Adversarial finding

**Severity:** P2 — The `rrule` library defaults `dtstart` to `new Date()` when the RRULE string
lacks `DTSTART`. This app's stored RRULEs never include `DTSTART` (confirmed in
`RecurrenceMenuField.tsx`'s `buildRRule()`). Without explicit `dtstart`, `.after(anchorDate)` may
not find occurrences when anchor is before dtstart. **Addressed by:** Parse RRULE options via
`RRule.parseString()`, then construct `new RRule({ ...parsedOptions, dtstart: anchorDate })` to
ensure occurrences are computed relative to the correct anchor.

### Files to create/modify

- `web/src/lib/staleness.ts` (NEW) — Three pure exported functions:
  `computeNextOccurrence(rruleStr, afterDate)` for anchor-relative next due date,
  `computeStaleness(taskFields, statusCategory, now?)` for the full ratio, `stalenessColor(ratio)`
  for green→yellow→red interpolation. Explicit `dtstart` override on RRule construction.
- `web/src/lib/staleness.test.ts` (NEW) — Unit tests for all three functions: daily/weekly/monthly
  intervals, multi-day rules (BYDAY=MO,TU), one-off guard, null rule guard, completion guard,
  lastCompletedAt vs createdAt fallback, color at key ratios.
- `web/src/components/task/TaskRow.tsx` (MODIFY) — Import staleness utilities. Add `useMemo`
  computing staleness. Conditionally render absolutely-positioned 3px indicator div with
  IconTooltip. Add `relative` to Link className.

### Test strategy

Unit tests in `staleness.test.ts` (vitest). No component tests — TaskRow change is a small
`useMemo` + conditional render, verifiable visually. Tests cover:

- `computeNextOccurrence`: daily, weekly, biweekly, monthly, yearly, multi-day (BYDAY=MO,TU,FR),

- `computeStaleness`: one_off→null, null rule→null, completion→null, correct ratio for known
  anchor/now pairs, createdAt fallback
- `stalenessColor`: green at 0, yellow at 0.5, red at 1.0, clamped above 1.0
